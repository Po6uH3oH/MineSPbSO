# Модель проверки входа

Лаунчер не доказывает неизменность клиента. Открытый клиент можно модифицировать. Цель — подтвердить аккаунт и не пустить сторонний клиент только по знанию ника.

1. Electron хранит refresh token с помощью `safeStorage` (Windows DPAPI). Renderer не получает access/refresh token; игра получает только случайный секрет локального брокера и его loopback-адрес. Пароль используется только при HTTP-запросе входа/регистрации и очищается из поля после успеха.
2. Minecraft соединяется с TCP listener на случайном loopback-порту. Electron создаёт TLS 1.3 соединение с настроенным шлюзом, проверяя сертификат/имя. Для разработки используется отдельный локальный CA PEM; отключения проверки сертификата нет.
3. Сервер Minecraft слушает **только 127.0.0.1:25565**. Серверный мод отказывается стартовать при другом bind или online-mode=true. Node TLS gateway открывает 25566/TCP. Это транспортный шлюз, без Velocity/Bungee и без подмены UUID.
4. Обязательный configuration payload не объявлен optional. Сервер получает профиль из `ServerCommonPacketListenerImpl.getOwner()` — проверено по mappings Mojang 1.21.1 и `javap`: метод публичный и возвращает `playerProfile()`. Он запрашивает challenge у сервиса с серверным секретом. Challenge содержит серверный идентификатор, точный ник, UUID, срок 60 секунд и случайный ID 256 бит.
5. Клиентский мод принимает запрос только от loopback-подключения с портом `SMP_GAME_PORT`, переданным лаунчером. Это препятствует получению билета через сторонний сервер, на который игрок перейдёт вручную. Адрес брокера не принимается из игрового пакета.
6. Брокер с отдельным 256-битным секретом запрашивает `/join/ticket` с access token. Только подтверждённый, не заблокированный аккаунт с выбранной фракцией и совпадающим точным ником/UUID может заполнить билет challenge. Медленная загрузка JVM не расходует время challenge.
7. Сервер принимает ответ только для challenge текущего listener. Один SQL UPDATE атомарно помечает билет использованным; повтор, истечение, другая учётная запись или блокировка отклоняются. Только после ответа сервиса вызывается `finishCurrentTask`.
8. Сбой/таймаут сервиса отключает клиента. Локального allowlist-обхода или резервного «доверять нику» нет.

## Границы

- Без TLS активный посредник может захватить уже подтверждённое offline-соединение. Проверки повторного использования билетов сами по себе этого не предотвращают. Рабочий Minecraft-порт нельзя открывать наружу.
- Локальный вредоносный процесс от имени игрока и мод с произвольным выполнением кода может получить доступ к памяти/брокеру/DPAPI того же пользователя. Это вне защиты от сетевой подмены ника. Дополнения разрешаются по SHA-256 владельцем; это не песочница для Java-модов.
- Регистрационные данные и конфигурации модов могут синхронизироваться в configuration-фазе до нашей задачи. Игровой мир, сущность игрока и инвентарь не создаются до завершения задачи. Реальный вход на 21.1.256 пока не проверен из-за Maven.
- Блокировка проверяется при каждом новом входе. Для немедленного удаления уже подключённого пользователя администратор также выполняет `kick` в серверной консоли; автоматического push-отключения ещё нет.
- Смена фракции применяется при следующем входе. Ник неизменяем. Отмена регистрации/удаление аккаунта интерфейсом не реализованы.
- Частота запросов ограничена по IP в Fastify и по хешу email/аккаунту в PostgreSQL. При reverse proxy `trustProxy=false`: без явной настройки доверенных адресов все запросы видны как запросы proxy. Нельзя слепо доверять X-Forwarded-For; production требует настроить доверенный proxy и его собственные лимиты.
- SQL использует параметры. В диагностике нет сырого HTTP, аргументов запуска, email, токенов или игровых журналов. Файлы исходных логов Minecraft не включаются в экспорт.
- Launcher update выключен без подписанной конфигурации. `signedUpdates=true` — не подпись; нужна реальная Authenticode-подпись и `publisherName` в конфигурации сборки. Текущий установщик unsigned.
